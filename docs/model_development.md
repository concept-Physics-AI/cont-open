# ConT 실제 AI 모형·연산자 개발 준비 상세

> 상태: 보조

기준 코드: `cd7a63ce705fa0553e2e0682fb8d7a8205638b32` (2026-11-25). 실행·인수는 [통합 정본](integration_control_plan.md), 작업 정의는 [integration_jobs.yaml](integration_jobs.yaml), 모형 능력 계약은 [model_readiness.yaml](model_readiness.yaml)을 따른다. 아래 계약은 개발 목표이며 아직 제공하지 않는 API를 현재 API처럼 사용하지 않는다.

## 1. 무엇을 직접 개발하는가

ConT의 독자성은 기반모형 하나를 처음부터 학습하는 데 두지 않는다. 현실 대상의 명세·조건·부품·시간·변경 이력을 공유하면서 대화, 이미지, 계산, 3D·4D, 선택 편집, 저장을 실행하는 소프트웨어와 물리 모형 구조를 직접 개발한다. 기반 LLM·VLM·이미지 생성모형은 교체 가능한 추론 공급자로 연결한다. 실제 실패의 종류와 빈도가 쌓인 뒤에 미세조정 또는 자체 학습의 필요를 판단한다.

현재 만드는 13개 슬롯은 능력과 책임의 구분이다. LLM_CHAT·LLM_PLAN·SCENE_SPEC은 같은 기반모형을 공유할 수 있다. INVERSE_OPERATOR·RESIDUAL_OPERATOR는 물리 연산자이며 독립된 거대모형이 아니다. M01~M10은 제품 기능 분류이고, 아래 슬롯은 구현 계약 분류다.

| 능력 슬롯 | 우선 구현 | 재사용할 기반 | 첫 인수 증거 |
|---|---|---|---|
| LLM_CHAT | 프로젝트 문맥 조립·후속 지시·확인 질문 | `cont.llm`, `dialogue.context` | 실제 10턴 대화와 상태 개정 |
| LLM_PLAN | 허용 도구 기반 구조화 계획·재계획 | `dialogue.plan`, `plan_tools` | 실제 LLM 계획에서 실행된 도구 목록 |
| VLM_INPUT | 원본 위치가 있는 이미지·도면·표 추출 | LLM 어댑터·CSV/형상 파서 | 원본-추출-사용자 정정-계산 입력의 연결 |
| IMAGE_CREATE | 명세 기반 실제 이미지 생성 | `generation`, `objspec.image` | 실제 이미지·모델·해시·대상 버전 |
| IMAGE_EDIT | 참조·마스크·선택 영역 수정 | 생성 어댑터에 편집 계약 추가 | 부모/마스크/새 이미지와 영역 안팎 검토 |
| SCENE_SPEC | 그래프·3D·4D 사양·부분 수정 | `objspec`, `view.scene4d` | 부품·단계·시점 일치와 실제 화면 동작 |
| KNOWLEDGE_RETRIEVAL | 문서 근거·접근 범위·검색 결과 | 기존 어댑터 경계를 준수해 연결 | 근거 위치·인용·권한 시험; 핵심 흐름의 선행조건 아님 |
| PINN_HEAT | 기존 열 네트워크·문제·잔차·상태 분리 | `learn.heat1d/heat2d/pack` | 자동 학습 없는 생성·조회·저장·기준 온도장 |
| PINN_STRUCTURE | 봉/보 한 문제의 모형·잔차 | 기존 FEM·공통 결과 형식 | 정한 지원 범위의 기준 구조 계산과 SW 시험 |
| PINN_VIBRATION | 단일 자유도 응답 모형·잔차 | 공통 학습/신호/결과 모듈 | 기준 ODE 응답·시간축·미분 연산 |
| PINN_FLOW | 기준해가 있는 관/채널 한 문제 | 공통 모형·결과 인터페이스 | 지원 가정·경계·기준 유동장·잔차 |
| INVERSE_OPERATOR | 관측 투영·미지 파라미터·기준 역산 | `learn.inverse_heat/gate` | 위치/시간 투영·누락·비유일성 처리 |
| RESIDUAL_OPERATOR | 방정식·경계·초기·보존·관측 차이 | 기존 Residual과 열 잔차 연산 | 종류·단위별 잔차와 기준 함수 시험 |

## 2. 공통 입출력 계약을 먼저 고정한다

아래는 새 타입 이름을 무조건 만드는 지시가 아니다. 기존 ObjectSpec, ViewState, PhysicsAnswer, RunStore, 원장 ID에 필드를 매핑하고, 부족한 계약의 책임 모듈을 ARCHITECTURE에서 정한 뒤 구현한다.

| 계약 | 필수 정보 | 갱신/검사 원칙 | 담당 작업 |
|---|---|---|---|
| 프로젝트 문맥 | project_id, revision, conversation refs, object refs, active selection | 소유권 검사 후 로드; 저장 revision 충돌 시 재조회 | GF02·GF13 |
| 대화 요청 | 사용자 메시지, 관련 이전 대화, 현재 대상·선택·조건, 허용 도구 | 전체 이력을 무조건 넣지 않고 관련 문맥과 근거를 조립; 요약에 원본 참조 | GF03 |
| 계획 | plan/step ID, 도구 이름, typed args, dependency refs, expected outputs | 순환·미등록 도구·빠진 대상·허용하지 않는 경로 차단 | GF03·GF04 |
| 선택 | project/artifact/object version, part/series/stage ID 또는 region, 좌표계 | 클릭 시점과 수정 시점의 버전 확인; 모호한 대상은 후보 반환 | GF08 |
| 이미지 결과 | 파일 hash, model/provider revision, params, real, parent, spec version | prompt 부품 선언과 픽셀 일치 상태를 별도 필드로 보존 | GF05·GF09 |
| 그래프 | 원본 run/field/data refs, 축·단위·계열·샘플·변환 | 원본 값과 표시값 변환 이력; 결측/보간 표시 | GF06 |
| 장면 | ObjectSpec version, 부품 매핑, 단계, ViewState, time_kind | 설명 단계 시간·물리 시간·재생 시간 분리 | GF07·PF08 |
| 물리 결과 | 실제 method, 문제/조건/단위/좌표/시간, fields, residuals | LLM이 숫자 배열을 작성해 해석 결과로 등록하지 않음 | PF02·PF08 |
| 산출물 개정 | artifact_id, parent refs, 입력 지문, dependency refs, stale 상태 | 덮어쓰기 없이 새 버전 발행; 영향받지 않는 결과 유지 | GF10 |
| 실행 증거 | commit, environment, model/config, 입력/출력 hash, command, result | pass/fail/skip/not_run 구분; 다른 개정 증거의 적용 범위 검토 | CT03·CT05 |

시간 계약은 특히 먼저 정한다. 본딩 접근·정렬·접촉의 설명 장면에서 정렬을 느리게 하는 것은 재생 변경이다. 계산된 열응답의 시간 간격을 바꾸려면 별도의 계산 입력 변경이 필요하다. 같은 슬라이더가 두 의미를 동시에 바꾸지 않도록 한다.

## 3. 대화와 계획 모형 개발 순서

1. GF01에서 선택 공급자에 실제 요청을 보내고 응답·오류·지연을 기록한다. 설정 파일의 공급자 이름만으로 준비 완료로 표시하지 않는다.
2. GF02에서 본딩 프로젝트 하나의 대화·대상·산출물을 저장한다. 이후 요청에 이 프로젝트 상태를 다시 넣는다.
3. GF03에서 계획 출력 스키마와 도구 목록을 먼저 고정한다. LLM은 사양을 제안하고 코드 검증기가 실행 가능 여부를 판단한다.
4. 설명·이미지·그래프·장면 도구를 각각 등록한다. 도구 출력은 기존 산출물 ID로 참조한다. 결과를 다음 단계의 자연어로만 전달하지 않는다.
5. “위 다이만 두껍게”, “두 번째 단계만 느리게”, “방금 변경을 취소”를 상태 변경 요청으로 해석한다. 대상이 둘 이상이면 확인 질문을 한다.
6. GF04/GF10에서 실패·취소·재시도·이전 버전·관련 결과만 재생성을 연결한다. 실제 요청 로그와 상태 개정으로 인수한다.

자연어 표현이 유사해도 처리 경로가 다르므로 평가 입력에 함께 넣는다: “다이를 크게 보여줘”(보기 변경), “다이 크기를 늘려줘”(형상 변경), “시간을 느리게”(재생/물리 시간 확인). 정답 문자열 일치보다 올바른 대상·도구·인자·영향 범위를 본다.

## 4. 이미지 생성·편집 모형 개발 순서

SDXL 실제 생성 1회 기록은 [generation.md](generation.md)에 있다. 지시와 그림이 완전히 일치하지 않은 결과도 기록되어 있으므로 실행 성공과 의미/품질 인수를 구분한다. 기존 `service.project`는 명세·카메라·선택·재생 위치·이미지 기록을 저장/복원한다. 대화·계획까지 이 저장에 통합하는 일이 GF02/GF11의 남은 범위다.

현재 `objspec.image`는 명세의 부품 목록을 이미지 요청에 넣고 기록한다. 이것은 실제 그림에 그 부품이 정확하게 그려졌다는 보장이 아니다. 현 이미지 생성 요청에 참조 이미지·마스크 편집 계약이 없으므로 GF09에서 확장한다.

1. 실제 생성 공급자의 라이선스·설치·추론·메모리·요청 제한을 확인하고 실행 정보를 남긴다. 특정 설정값을 모든 환경의 기본 성능으로 가정하지 않는다.
2. 생성 요청에 ObjectSpec version과 부품 선언을 기록하고, 실제 이미지 파일과 원본 해시를 저장한다.
3. 참조 이미지·부모 버전·마스크 좌표·크기·수정 지시를 별도 편집 계약으로 만든다. 공급자가 편집을 지원하지 않으면 미지원으로 반환한다.
4. 원본과 편집 결과를 나란히 보여주고 선택 안팎의 변경을 확인한다. 부품 ID 보존은 명세 계층에서 검사하고 이미지 픽셀의 의미 일치는 별도 검토한다.
5. 글자·단위·치수처럼 정확해야 하는 표시는 계산/명세에서 렌더링한 오버레이로 처리한다. 이미지 모형이 그린 문자를 계산 정답으로 사용하지 않는다.
6. 결과를 프로젝트에 저장하고, 파일 누락·모델 실패·취소·재열기에도 원본을 보존한다.

## 5. 자체 PINN 모형을 새 학습 없이 구현하는 범위

PINN 소프트웨어를 만들고 미분·잔차를 시험하는 일은 지금 할 수 있다. 무작위 가중치 상태의 신경망이 정확한 물리해를 내도록 하는 것은 현재 인수 요구가 아니다. 후속에 신경망을 실제 해의 근사기로 사용하려면 문제별 최적화 또는 적절한 기존 가중치와 별도 평가가 필요하다.

현재 모형 준비 상태는 다음 세 축으로 구현한다. 이 표는 계약안이며 런타임에 이미 존재하는 상태 열거형이 아니다.

| 축 | 상태 예 | 의미 |
|---|---|---|
| 소프트웨어 | defined / constructed / software_checked / failed | 문제·네트워크·입출력·미분·저장 기능의 준비 |
| 가중치 | absent / present_unverified / evaluated | 가중치 유무와 해당 문제에 대한 평가 여부 |
| 물리 결과 경로 | reference_available / reference_unsupported / neural_inference_enabled | 실제 값을 어느 방법으로 얻을 수 있는지 |

가중치가 없으면 사용자에게는 미학습(`untrained`)으로 표시한다. 소프트웨어 시험이 통과했다고 neural_inference_enabled로 올리지 않는다. 기준 계산이 있으면 그 방법으로 결과를 내고, 없으면 미지원으로 알린다. 실제 가중치가 있어도 문제·단위·정규화·출력 계약이 맞고 해당 범위 평가를 통과하기 전에는 추론을 활성화하지 않는다.

**PF01에서 먼저 바꿀 것:** 현재 `learn.pack`의 첫 조회 자동 학습 경로를 일반 조회에서 분리한다. 연구용 학습 함수는 보존한다. 프로젝트 조회·모형 생성·기준 계산·저장·복원 시험에서는 학습 진입점과 optimizer 실행을 감시하거나 차단한다. 새 학습 호출이 있으면 실패한다.

**PF02에서 공통으로 구현할 것:** 문제 사양, 물성, 형상, 좌표/시간 단위, 초기·경계조건, 입력/출력 차원, 정규화, 미분 차수, 잔차 함수, 기준 계산 어댑터, 모형 설정 기록을 분리한다. 저장한 설정으로 같은 구조를 만들 수 있어야 한다. 난수 초기화의 재현성은 SW 시험용이며 물리 정확도 근거가 아니다.

| 물리 영역 | 첫 지원 문제 | 입력 | SW 출력과 실제 물리 출력 | 주요 실패 시험 |
|---|---|---|---|---|
| 열 | 기존 1D·2D 열 문제 중 지원 범위 고정 | 좌표·시간·열물성·초기/경계 | 네트워크/잔차 구성 + 기존 해석기의 온도장 | 단위·열물성·경계 누락, 첫 조회 학습 |
| 구조 | 봉 또는 보 한 문제 | 재료·단면·하중·구속 | 변위 네트워크/잔차 + 지원 기준해의 변위/응력 | 미지원 접촉·비선형·구속 부족 |
| 진동 | 단일 자유도 질량·스프링·감쇠 | 계수·외력·초기값·시간 | 응답 네트워크/잔차 + 기준 ODE 응답 | 잘못된 계수·시간 단위·초기조건 |
| 유동 | 기준해가 있는 단순 관/채널 | 형상·점성·경계·가정 | 속도/압력 네트워크/잔차 + 기준 유동장 | 가정 위반·미지원 형상·압력 기준 누락 |

구조·진동·유동의 첫 문제를 모두 일반 산업 문제로 확대하지 않는다. 각 한 문제의 코드·입출력·실패 처리·기준 계산·저장·화면이 이어진 뒤 지원 문제를 하나씩 늘린다.

## 6. 숨은 물리와 잔차

PF03은 관측을 모델 상태로부터 읽어내는 연산과 미지 파라미터의 범위를 먼저 만든다. 측정 위치·시각·값이 없는 상황에서 숨은 물리를 식별했다고 보고하지 않는다. 기존 기준 역산을 연결하는 경우에도 실제 방법, 관측 조건, 민감도, 정보 부족을 기록한다. 구현하지 않은 불확실성은 수치를 만들어 채우지 않는다.

PF04는 PDE·경계·초기·보존·관측 잔차를 따로 계산한다. 종류별 단위와 정규화 기준을 함께 저장한다. 알려진 함수와 기준해에서 잔차 연산을 시험하고 수치 이산화의 영향을 확인한다. 작은 잔차만으로 실제 공정 정확도를 보장하지 않는다. 보정 모형 포트는 마련하되 가중치가 없으면 적용하지 않는다.

PF08은 잔차와 기준장을 같은 부품·좌표·시간에 연결한다. 모형 준비 상태와 실제 계산 방법이 함께 저장되어야 한다. 시각적 보간, 변형 배율, 입자 효과는 원본 값과 구분한다.

## 7. 환경·자원 준비와 교체 전략

| 준비 항목 | 지금 확인할 것 | 준비 증거 |
|---|---|---|
| 실행 환경 | Python/Node/선택 의존 버전, CPU/GPU, 가용 메모리, 저장 용량 | 환경 manifest와 실제 프로세스 로그 |
| 공급자 | 접근 가능 여부, 인증 위치, 모델 revision, 지원 기능 | 실제 최소 요청과 오류 분류 |
| 가중치 | 존재·해시·라이선스·사용 범위 | 외부 보관 위치 참조; 저장소에 가중치/비밀값 금지 |
| 자원 경쟁 | 텍스트·이미지·물리 작업의 동시 실행 가능 여부 | 실제 측정 후 동시성/대기/해제 설정 |
| 중단·회수 | 시간초과·취소·메모리 부족 뒤 자원 반환 | 재실행 성공과 중복 반영 없음 |
| 교체 | 공급자별 capability와 출력 정규화 | 동일 계약 시험과 프로젝트 구버전 읽기 |

특정 GPU가 있다는 과거 기록만으로 이번 실행 환경이 준비됐다고 판단하지 않는다. 단일 GPU에서는 실제 측정에 따라 이미지 생성과 다른 모델을 대기열로 순차 실행할 수 있다. 성능 수치는 실제 측정 후 config에 둔다. 사용자는 작업 대기·실행·실패를 볼 수 있어야 한다.

## 8. 모형 준비 판정과 인계

모든 슬롯의 현재 제품 통합 인수는 `pending`으로 등록했다. 기존 모듈·연구 결과를 삭제하거나 미구현으로 되돌리는 뜻이 아니다. 계약 정의, 어댑터 연결, 실제 추론, 사용자 흐름 인수를 각각 증거로 남긴다.

- 생성형 공급자 인수: 실제 모델 식별·요청·응답/파일·실패 처리·비용/지연 관측. 시험용 생성기는 계약 시험만 통과시킨다.
- PINN SW 인수: 가중치 없이 구성·미분·잔차·기준 계산·저장/복원이 동작하고 새 학습 호출이 없다. 예측 정확도 인수가 아니다.
- 화면 인수: 실제 클릭·선택·회전·시간 변경·재수정·저장/재개가 하나의 프로젝트에서 이어진다.
- 다음 개발자 인계: 슬롯 ID, 작업 ID, 계약 개정, 실제 지원 기능, 미지원 범위, 재현 입력, 실행 명령, 결과, 다음 한 단계.

M05~M09의 전문 학습은 이 흐름의 필수 선행조건으로 추가하지 않는다. 후속 학습을 시작할 때에는 해결할 실패 유형, 자료 권리, 독립 평가 분할, 기준선, 기대 개선, 되돌릴 방법을 별도 작업으로 등록한다. 현재 계획 작성이나 정적 검사 실행은 학습을 시작하지 않는다.
