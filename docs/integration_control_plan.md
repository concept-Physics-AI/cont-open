# ConT 제품 통합 작업·컨트롤타워·인수 계획

> 상태: 보조

기준 코드: `27708280c15d4266068ec43b91947ce1c8a8af58` (2026-11-25). 이 문서는 개발 계획이며 기능 구현 완료 보고가 아니다. 제품 방향과 모듈 경계는 [ARCHITECTURE.md](../ARCHITECTURE.md), 개발 규칙은 [CLAUDE.md](../CLAUDE.md), 제품 우선순위는 [roadmap.md](roadmap.md)를 따른다.

**생성형 기능을 최우선으로 완성하고, PINN은 다양한 물리·숨은 물리·물리 잔차의 자체 모형 SW를 새 학습 없이 병행 구현한다. 모형 학습과 대규모 현장 데이터 학습은 후속이다.**

후속 대표 지시에 따라 PF01~PF08은 학습 실행과 학습된 가중치 없이 인수할 수 있도록 수정했다. 자체 모형의 코드·구조·연산·저장·화면을 구현하는 단계이며 신경망의 예측 정확도가 이미 확보됐다는 뜻은 아니다. 실제 물리 값은 기존 해석식·수치해석을 명시해 사용한다.

## 1. 현재 있는 계획과 이번에 채우는 부분

| 구분 | 현재 구현/문서 | 현재 한계 | 이번 계획의 자리 |

| 물리/PINN | 열 1D·2D·역문제·잔차·범위 처리 | 다물리 확장·영속 모델·화면 통합 부족 | PF01~PF08; 생성형 전체 완료를 기다리지 않음 |

현재 `tests/test_control_tower.py`는 파일·문구·상태 형식의 일부를 검사한다. 파일 존재만으로 실제 사용자 경험의 성공을 증명하지 못한다. 이번 문서와 YAML 추가가 자동 컨트롤타워의 구현을 뜻하지 않는다.

기존 문서 중 `generative_outputs`의 본딩 장면 부재 표현과 `objspec.md` 첫 문장의 장면 연결 부재 표현은 PR #100 이후 코드보다 오래됐다. CT01에서 코드·시험·실행 증거를 대조해 바로잡는다. 하나의 현황 문장만으로 신규 개발 여부를 판단하지 않는다.

## 2. 작업 정의와 상태의 기준

**작업 명세의 정본은 [integration_jobs.yaml](integration_jobs.yaml)이다.** 아래 표는 탐색용이다. YAML은 32개 작업에 id, title, track, owner_role, owner, planning_state, depends_on, reuse_paths, deliverables, acceptance, negative_tests, rollback, evidence_required를 제공한다.

- 모든 `planning_state: planned`는 이번 통합 작업이 아직 배정·인수되지 않았다는 뜻이다. 기존 모듈의 구현 상태를 없음으로 바꾸는 뜻이 아니다.
- `owner_role`은 필요한 역할이다. 실제 담당자 `owner`는 미지정이며 특정 인원이나 자동 에이전트에게 작업을 시작시킨 것이 아니다.
- `depends_on`은 통합 인수 선행조건이다. 인터페이스 설계와 독립 구현을 먼저 할 수 있지만 시험용 응답으로 연결 인수를 통과시키지 않는다.
- 현존 제품 기능 상태는 `config/status.yaml`에서 관리한다. 작업별 상태로 그 파일의 있음/뼈대/없음을 대체하지 않는다.
- 코드 증거는 현재 경로를 재사용한다. 신규 책임 모듈·계약·API는 해당 작업에서 ARCHITECTURE와 책임 표를 먼저 정한 뒤 추가한다. 이 계획이 아직 없는 API를 이미 제공한다고 선언하지 않는다.

## 4. 실행 묶음과 의존 관계

기간과 인력은 아직 확정하지 않았다. 기존 로드맵 원칙대로 아래는 일정 약속이 아닌 구현·인수 순서다. CT 관리 기능 전체가 완성될 때까지 생성형 개발을 기다리게 하지 않는다. CT01 이후 초기 작업은 PR과 수동 증거표로 추적하고 CT02~CT05가 갖춰지면 그 기록을 가져온다.

| 묶음 | 생성형 주 개발 | PINN 병행 | 이 묶음을 나가는 조건 |
|---|---|---|---|
| A: 기준과 실행 준비 | CT01, GF01·GF02; CT02 최소 기록 | PF01·PF02 착수 | 실제 공급자 실행, 최소 프로젝트·대상 계약, 기준 재현 기록 |
| B: 실제 생성 연결 | GF03~GF07; CT03·CT05 | PF03·PF04 | 실제 요청이 계획·이미지·그래프·본딩 장면으로 이어짐 |
| C: 편집과 복원 | GF08~GF11; CT04 | PF05~PF07을 담당/자원에 맞춰 순차 또는 독립 진행, PF08 | 선택 수정·영향 갱신·종료 후 복원; 물리 결과는 별도 인수 |
| D: 입력과 제품화 | GF12~GF14, QA01~QA04, CT06 | 통과한 물리 문제만 제품 도구에 연결 | 대상 릴리스의 필수 인수 완료, 실패/미지원/복귀 절차 명시 |

대표적인 생성형 의존 경로는 GF01/GF02 → GF03 → GF04, GF02 → GF05/GF06/GF07 → GF08/GF09/GF10 → GF11 → QA01이다. 정확한 선행조건은 YAML의 DAG를 따른다. PF05~PF07의 전부 완료는 QA01의 선행조건이 아니다. 물리 통합을 포함한 릴리스에서는 PF08과 그 릴리스에서 사용하는 물리 문제의 인수 증거가 추가로 필요하다.

## 5. 컨트롤타워의 구체적인 운영 설계

### 세 가지 기록을 분리한다

| 기록 | 목적 | 연결 키 | 현재/계획 |
|---|---|---|---|
| 개발 작업 | 누가 어느 기능을 어떤 증거로 인수했는가 | task_id, branch, tested_commit, evidence_id | 이번 작업 정의와 CT02~CT03 구현 계획 |
| 사용자 작업 실행 | 사용자의 요청을 어느 도구로 어디까지 처리했는가 | project_id, request_id, run_id, step_id, attempt | 기존 실행기·저장소를 GF03~GF11로 확장 |
| 물리 모형/계산 | 어떤 문제·모형 상태·설정·기준 계산에서 결과가 나왔는가 | problem_version, model_state, method, evaluation_run; 가중치가 있을 때만 model_hash | 현재 무학습 SW 계약. training_run은 후속 학습에만 사용 |

개발 컨트롤타워가 사용자 도구 실행기를 새로 복제하지 않는다. 각 기록은 서로 참조하고 동일 개념은 기존 책임 모듈에서만 정의한다.

### 작업 상태 전환 (CT02에서 구현할 규칙)

`planned → ready → in_progress → implemented → checked → accepted`

- planned: 정의만 있다. 담당·입력·환경·증거가 준비되지 않아도 등록 가능하다.
- ready: 담당, 변경 범위, 선행 인터페이스, 필요한 실행 환경, 시험 계획이 정해졌다.
- in_progress: 담당이 브랜치/기준 커밋/변경 파일 범위를 등록했다. 같은 파일의 활성 변경은 조정한다.
- implemented: 코드와 단위 시험은 있다. 실제 모델/화면 인수가 남을 수 있다.
- checked: 이 작업에 요구되는 시험을 수행했고 실행 증거가 현재 변경에 대응한다.
- accepted: YAML의 인수 항목을 모두 충족하고 담당 외 검토 역할 또는 제품 책임의 확인이 기록됐다. 최종 PR 병합 권한은 기존 CLAUDE 규칙을 따른다.
- blocked: 어느 단계에서든 전환 가능. 원인, 해결 담당, 필요한 입력, 재개할 이전 상태를 기록한다. 시간 경과만으로 자동 해제하지 않는다.
- cancelled: 범위 변경으로 종료. 이유와 대체 작업 ID를 남기고 산출물은 보존한다.

`skip`은 작업 완료 상태가 아니다. 필수 인수 시험이 skip이면 checked/accepted로 올리지 않는다. 선택 시험의 skip은 사유와 해당 릴리스 범위를 기록한다. 코드/설정/모델/입력 계약이 바뀌면 영향받는 증거를 재검토 표시로 돌린다. 문구 수정만으로 모든 물리 시험을 무조건 다시 돌리는 규칙은 만들지 않는다.

### 담당과 충돌 관리

한 작업에는 책임자 한 명을 지정한다. AI 도구 이름만 적는 경우에도 실제 브랜치와 작업 세션을 식별하고 통합 책임자가 소유권을 확인한다. 실제 역할 배정은 아직 없다. 같은 사람이 여러 역할을 수행할 수 있으나 자기 완료 선언만으로 실제 인수 증거를 대체하지 않는다.

- 공통 계약 변경은 ARCHITECTURE·책임 모듈 표를 먼저 검토한다.
- 한 브랜치 한 작업을 원칙으로 하고 여러 PR이 필요하면 하위 범위를 부모 작업에 연결한다.
- 다른 작업자가 건드린 파일을 덮어쓰지 않는다. 최신 main을 확인하고 충돌 해결 후 영향받는 시험을 수행한다.
- 생성형 모델과 PINN이 같은 GPU를 사용하면 실행 큐·취소·메모리 예산을 둔다. 모델을 동시에 올려야만 병행 개발인 것은 아니다.
- 대시보드는 기록 조회부터 만든다. 자동 예약 검사, 메일/메신저 알림, 모델 자동 학습을 이 계획만으로 시작하지 않는다.

### 완료 증거 묶음 (CT03 제안 계약)

아래는 아직 구현된 API가 아닌 기록 계약 제안이다. 실제 파일/데이터는 접근 통제된 저장소에 두고 공개 PR에는 민감하지 않은 요약과 접근 가능한 증거 참조만 남긴다.

```yaml
task_id: GF07
tested_commit: <검사한 커밋>
input_revision: <프로젝트·대상·조건 개정>
environment: <OS·Python·브라우저·GPU·의존성 버전>
provider: <실제 공급자·모델 또는 해당 없음>
execution: <실행 명령 또는 화면 조작 순서>
evidence:
  - kind: contract_test
    result: <pass|fail|skip|blocked>
    artifact_ref: <접근 통제된 로그 참조>
    sha256: <파일 해시>
  - kind: browser_acceptance
    result: <pass|fail|skip|blocked>
    artifact_ref: <화면·이벤트·산출물 참조>
    sha256: <파일 해시>
remaining: <실패·미지원·건너뜀과 이유>
review: <검토 역할·시각·판단 근거>
```

화면 캡처만으로 내부 수치·저장 복원을 증명하지 않는다. 화면·실행 이벤트·원본 자료·산출물 해시를 함께 연결한다. 기존 자료 장부는 실행 산출물의 계보에 재사용하되 개발 작업의 담당·PR 상태까지 억지로 같은 객체로 합치지 않는다.

### 대시보드에서 반드시 보일 것 (CT04)

1. 기준 커밋, 현재 읽은 스냅샷 시각, 실제 실행 버전.
2. 작업별 담당·상태·브랜치·선행 작업·차단 원인·다음 행동.
3. 제품 여섯 기능의 실제 모델/화면/복원 인수 여부와 증거 링크.
4. PINN의 물리 영역·문제·모형 상태·잔차 연산·기준 계산 방법·적용 범위. 미학습에는 수렴/예측 성능 값을 만들지 않음.
5. pass/fail/skip/blocked 개수, 사용한 실제 모델과 시험용 공급자의 구분.
6. 전체 완료율을 보여줄 때 분모·작업 범위·가중치 여부. PR 수나 코드 줄 수를 제품 완성률로 쓰지 않음.

## 7. 실제로 돌릴 검사와 현재 범위

다음 명령은 현재 저장소에 존재한다. 개발 환경을 설치한 뒤 저장소 루트에서 실행한다.

```bash
python -m pytest -q tests/test_docs_status.py tests/test_control_tower.py tests/test_authority.py
python -m pytest -q tests/test_dialogue_context.py tests/test_dialogue_plan.py tests/test_dialogue_plan_store.py tests/test_dialogue_plan_tools.py
python -m pytest -q tests/test_generation.py tests/test_objspec.py tests/test_scene4d.py
python -m pytest -q
```

- 실제 이미지 시험은 `CONT_GEN_REAL=1`과 `CONT_GEN_REAL_MODEL`로 설치된 모델을 지정하고 `tests/test_generation.py::test_real_model_makes_a_png`를 실행한다. 시험이 기본으로 skip된 경우 실제 이미지 인수로 계산하지 않는다.
- 기존 학습 회귀 시험(현재 무학습 SW 인수와 별개)은 PyTorch 설치 환경에서 `CONT_REQUIRE_TORCH=1`을 설정한 뒤 `python -m pytest -q tests/learn`을 실행한다. 이 변수는 선택 설치 누락으로 인한 건너뜀을 감추지 않기 위한 기존 CI 설정이다.
- 브라우저 시험은 Chrome/Chromium·Playwright·WebGL이 필요하다. 환경 미지원 시 건너뜀 이유를 기록하고 실제 화면 인수는 다른 지원 환경에서 수행한다.
- PF01~PF08의 무학습 인수 시험은 구현할 대상이다. 학습 함수 호출을 차단하고 구조/잔차 연산·기준 계산·저장/화면을 시험한다. 기존 tests/learn 통과를 이 인수로 대체하지 않는다.
- 실제 LLM 다중 턴, 전체 프로젝트 복원, 부분 편집 인수 자동화는 아직 없다. GF/QA 작업에서 만들기 전까지 위 명령이 모두 검사한다고 설명하지 않는다.
- 이번 계획의 YAML은 작성 시 ID 중복·의존 존재·DAG·재사용 경로를 검사한다. 이를 지속적으로 집행하는 등록기/상태 전환기는 CT02 이후 구현한다.

## 8. 작업별 개발 명령문과 완료보고

개발 도구에는 아래 명령문과 대상 작업 ID를 함께 전달한다. 모든 작업을 한 번에 완료했다고 주장하는 단일 지시로 쓰지 않는다.

> 최신 main과 ARCHITECTURE.md·CLAUDE.md·roadmap.md를 읽는다. integration_jobs.yaml의 지정 작업 한 건을 선택한다. 기준 커밋·담당·변경 파일·선행 인터페이스와 증거를 확인한다. reuse_paths의 구현을 읽어 재사용하고 새 책임 계약은 아키텍처에 먼저 반영한다. deliverables를 구현하며 acceptance와 negative_tests를 충족하는 시험을 수행한다. 더미/실제 생성형 모델/브라우저/PINN 무학습 SW/후속 학습/현장 시험을 구분한다. 현재 PF 작업은 학습 호출 0으로 인수하며 미학습 신경망 출력을 물리 예측으로 쓰지 않는다. 한 브랜치·한 범위 PR로 제출하고 실행 커밋·실행 방법·산출물·실패·skip·rollback을 보고한다. 실제 인수 증거가 없으면 implemented 상태에서 멈추고 완료로 올리지 않는다. 다른 담당자의 변경을 덮어쓰거나 무관한 물리 영역과 대규모 현장 학습을 추가하지 않는다.

완료보고 필수 항목:

| 항목 | 보고할 내용 |
|---|---|
| 작업 | ID·범위·담당·기준 및 결과 커밋·PR |
| 재사용/신규 | 재사용한 모듈·새 계약·바뀐 파일 |
| 사용자 동작 | 어떤 요청이 어떤 도구·결과·화면으로 이어지는가 |
| 검증 | 시험 명령·pass/fail/skip·실제 모델과 입력·환경 |
| 증거 | 원본/출력 해시·로그·화면·복원·물리 기준 대조 |
| 한계 | 미지원·미실행·차단 원인·다음 행동 |
| 복귀 | 이전 코드/설정/모델/프로젝트를 보존하는 방법 |

## 9. 첫 착수 묶음

CT01에서 최신 기준과 미완료 연결을 확정한 다음 GF01(실제 공급자 실행)·GF02(최소 프로젝트 상태)를 우선 착수한다. PINN은 PF01(학습 없는 모형 등록/조회/저장)·PF02(자체 모형 구조·문제·잔차 계약)를 병행한다. 그 다음 GF03~GF07로 본딩 한 건의 생성 흐름을 먼저 연결하고, PF03~PF08을 준비된 기준 문제별로 확장한다.

현재 담당·환경·실제 모델 실행 증거는 작업 카드에 배정되지 않았다. 따라서 이 계획을 등록했다는 사실만으로 ready나 accepted 작업 수를 올리지 않는다. 기존 코드의 준비 정도와 신규 통합 작업의 완료는 별도로 추적한다.
