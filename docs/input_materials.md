# 입력 자료: 무엇을 읽었고 무엇을 가져왔는가

> 상태: 참고

**현재 우선순위:** 2026-11-25 후속 대표 지시로 [여섯 핵심 생성·편집 기능](generative_workflow.md)을 우선한다. 아래 과거 입력의 자체 학습 중심·산업별 순서는 당시 제안의 출처 기록이며 현재 우선순위를 덮어쓰지 않는다.

이 저장소의 정본은 [ARCHITECTURE.md](../ARCHITECTURE.md)와 [CLAUDE.md](../CLAUDE.md)다. 옛 저장소와 대표 PC의 정본 문서 묶음은 **입력 자료**이며 이 저장소의 정본이 아니다.
공개 저장소이므로 입력 자료의 내용, 문서 ID, 경로, 회사 내부 자료, 출원 중인 특허 내용은 여기에 옮기지 않는다. 아래는 일반 원칙 수준으로 무엇을 가져왔는지만 적는다.

## 2026-11-25 이전 지시와 반영 기록 (아래 PINN 병행 정정 우선)

“데이터는 SW 개발 후 학습하도록 하고, AI 생성형 기능 구현에 집중하도록 방향을 명확하게 잡아주세요.”

반영: 기존 모델로 여섯 핵심 생성형 기능을 연결한 소프트웨어를 먼저 완성하고 실제 사용 평가를 진행한다. 학습용 데이터 확보·정리·라벨링과 신규 학습은 이후 필요한 범위만 검토한다. 사용자 입력·샘플·저장·오류 기록·소프트웨어 시험은 현재 개발 범위다. 정본은 [ARCHITECTURE.md](../ARCHITECTURE.md), 개발 규칙은 [CLAUDE.md](../CLAUDE.md), 실행 순서는 [roadmap.md](roadmap.md)다.

## 2026-11-25 PINN 병행에 관한 최종 정정

“생성형 기능을 최우선으로 완성하면서, PINN은 다양한 물리와 숨은물리, 물리잔차 기능으로 병행하고, 대규모 현장 데이터 학습은 나중에 진행한다.”

바로 위 입력의 신규 학습 일괄 보류 해석을 대체한다. PINN의 방정식 기반 학습·역문제·잔차 계산과 보정·기준 문제 및 합성 관측 시험은 현재 병행 범위다. 대규모 현장 데이터 학습을 이후로 두며 생성형 제품 흐름은 PINN의 완료를 기다리지 않는다. [ARCHITECTURE.md](../ARCHITECTURE.md)와 [roadmap.md](roadmap.md)에 반영한다.

## 가져온 원칙

| 원칙 | 이 저장소에서 어디에 있는가 |
|---|---|
| 한 개념은 한 곳에서만 정의한다 | `config/authority.yaml`, `tests/test_authority.py` |
| 물리 값은 엔진에서만 나오고, LLM은 값을 만들지 않는다 | CLAUDE.md 규칙 7, 서비스 층은 팩의 답을 그대로 돌려준다 |
| 관측한 것, 계산한 것, 생성한 것을 구분한다 | 값의 지위 (PhysicsAnswer) |
| 검증 상태는 문서 상태나 엔진 성공과 다르다. 합성 결과를 검증된 것처럼 올리지 않는다 | `config/status.yaml`, `tests/test_control_tower.py`의 "검증 완료" 점검 |
| 같은 결과인지 알아볼 표식을 둔다 (내용 해시, 개정) | `PhysicsAnswer.revision_id()`, `Provenance` |
| 규칙은 문서에만 두지 않고 점검으로 지킨다 | 컨트롤타워 최소판 |
| 문서는 상태를 표시하고, 새 문서보다 기존 문서 수정이 먼저다 | 문서 상태 5종, CLAUDE.md 규칙 2 |
| 공용 계약은 한 곳에서만 바꾼다 | 결과 형식 변경은 별도 PR |

대표 PC의 방향 문서 새 판, 열 영역 알고리즘 개발 보고서(개정판), 보존 목록을 읽었다. 목록은 스스로 "통합 최종본 아님"이라고 적고 있다. 방향 문서의 세부 문서 네 개는 본문을 받지 못해 읽지 못했다.

| 구분 | 내용 | 자리 |

| 가져옴 | 관측 연산자, 보정 파라미터, 식별 가능성, 오차 예산 구조 | [로드맵](roadmap.md) 6절 |
| 가져옴 | 위험을 추정 분포에서 낸 초과 확률로 보고 | 같은 곳 |
| 가져옴 | 합성 정답 시험과 음성 대조를 실제 기준 대조와 구분 | 로드맵 1번 조건 |
| 가져옴 | 학습은 물리 값과의 편차만 맡고 범위 밖이면 물리 값으로 복귀, 시료·로트 단위 분할 | 로드맵 3번 조건 |
| 미룸 | 열화상 방사 관측, 데이터 동화, 세계 모형 | 열 영역을 열 때 |

## 2026-11-24에 더 읽은 것 (실행 묶음 다섯 개)

대표 PC의 실행 묶음 다섯 개를 읽었다: 숨은 물리 알고리즘 연구 패키지(코드와 시험 포함), 숨은 물리 잔차 구조 문서, 제품 화면 실행 묶음, 조율 묶음, 3D·4D 실행 묶음. 연구 패키지의 시험은 돌려 보지 않았다 (묶음이 스스로 적은 결과를 확인하지 않았다). 코드는 옮기지 않고 방법만 우리 말로 적는다.

| 구분 | 내용 | 자리 |
|---|---|---|
| 가져옴 | 식별 가능성: 파라미터를 조금씩 흔든 정규화 민감도 행렬의 특이값으로 유효 순위와 조건수, 파라미터 상관을 낸다. 등급은 식별 불가, 조합만, 약, 실용, 강 | [로드맵](roadmap.md) 6절 2번 |

| 가져옴 | 단위: 온도처럼 오프셋이 있는 단위는 배율만 곱하는 변환기로 처리하지 않고, 변환 흔적을 남긴다 | 열 영역을 열 때 |

## 2026-11-24에 더 읽은 것 (묶음 열 개: 표현, 필드 변환, 대화, 물리 지식)

물리 이미지, 실제 영상, 3D·4D 표현, 메시와 복셀 사이의 필드 변환, 대화 AI 정밀 개발, 물리 수치 라이브러리와 재료 지식그래프, Studio 사양, 36권 백과를 훑었다. 표현·필드·대화·물리 지식 묶음의 개념 문서는 읽었고, Studio 사양, 4D 뷰어 설계서, 36권 백과, 물리 온톨로지 문서는 목차와 일부만 보았다. 대화 묶음의 시험(39개)은 돌려 보지 않았다. 코드와 문서 ID는 옮기지 않고 방법만 우리 말로 적는다.

**기준 자료로 쓸 수 있는 값은 없었다.** 재료 지식그래프의 시작 자료는 설명서가 스스로 "예시용이며 실제 값으로 쓰지 말 것"이라고 적고 있다. 로드맵의 "기준 자료를 어디서 구할지"는 그대로 열려 있다.

## 세 분야 개발 계획서 (2026-11-24 검토)

체결, 하이브리드 본딩, 휴머노이드 관절 세 분야를 한 제품에서 잇는 개발 계획서다. 원칙만 가져오고 [roadmap.md](roadmap.md) 4-1에 과제로 올렸다.

| 가져온 원칙 | 어디에 반영하는가 |
|---|---|
| 모든 실행에 프로젝트·대상·작업·실행 ID를 붙이고, 단위·좌표계·채널 의미·출처를 기록한다 | 로드맵 4-1 A (ARCHITECTURE.md에 먼저 적은 뒤 구현) |
| 실측값, 물리 계산값, AI 추정값, 검사 결과를 서로 다른 필드로 둔다 | 값의 지위(이미 있음)를 이 구분과 맞춘다 |
| 입력을 바꿔 다시 계산하면 새 실행이 생기고, 이전 검토와 화면은 원래 실행을 가리킨다. 승인한 실행과 최신 실행을 구분한다 | 4-1 A |
| 분야마다 입력, 1차 모델, 2차 모델, 검증, 화면, 초기 제외 범위를 적는다 | 4-1 B, D, E |
| 같은 최종 토크라도 마찰과 체결 조건에 따라 체결력이 다르므로 토크만으로 체결력이나 양품을 확정하지 않는다 | 체결 팩의 한계 표시(이미 있음) |
| 온도·하중·변위 센서만으로 계면 상태나 최종 접합 품질을 확정하지 않는다. 품질 판단은 접합 후 검사 데이터로 따로 검증한다 | 4-1 D의 초기 제외 범위 |
| 시뮬레이션의 성공만으로 실제 성능을 확정하지 않는다. 제어와 보호는 기존 제어기가 맡고 LLM이 실시간 제어 루프를 맡지 않는다 | 4-1 E, "LLM과 숫자" |
| 학습·보정에 쓰지 않은 데이터로 평가하고 작업일·로트로 나눈다. 미검출과 오경보를 분리하고 현행 규칙과 단순 물리 모델을 기준선으로 둔다. 하나의 정확도로 세 분야를 평가하지 않는다 | 4-1 C |
| 모델은 후보 학습, 고정 평가셋 비교, 검토, 배포 순서로 바꾸고 이전 버전으로 되돌릴 수 있다 | 4-1 F |
| 완료는 화면, 계산 검증, 현장 검증을 따로 확인한다. 실측 접근이 없으면 "연동 완료, 현장 검증 미완료"로 구분한다 | 증거 수준(E0~E2)과 검증 상태 |

## 대화·순차 생성·4D 개발명령문 (2026-11-24 검토)

대화로 이미지, 그래프, 3D, 4D를 차례로 만들고 고치는 개발명령문이다. 원칙은 [roadmap.md](roadmap.md) 4-1의 W로 올렸다.

| 가져온 원칙 | 어디에 반영하는가 |
|---|---|
| 일반 설명이나 창작 대화를 볼트 변수 추출기에 억지로 통과시키지 않고, 설명, 계산, 비교, 수정, 저장을 나눠 처리한다 | W2 |
| LLM 출력은 검증 가능한 계획 객체로만 받고 등록된 도구만 실행한다. 임의의 코드를 그대로 실행하지 않는다 | W3 |
| 완료된 결과부터 보이고, 실패한 단계만 다시 하며, 같은 요청은 한 번만 실행한다 | W3 |
| 생성 이미지와 계산으로 그린 물리 그림은 생성 경로를 따로 보관한다. 정확한 치수, 단위, 주석은 구조화된 데이터에서 그린다 | W4 ([generation.md](generation.md)의 규칙과 같다) |
| 4D는 축 종류(실제 시간, 공정 단계, 조건 변화)를 적고, 근거 없이 초 단위를 붙이지 않는다. 재생 속도는 물리 시간을 바꾸지 않는다 | W5 |
| 후속 수정은 변경 영향에 따라 필요한 부분만 새 버전으로 만들고 이전 결과를 남긴다 | W6 |
| 실제 공급자와 실제 브라우저로 인수하고, 자동시험, 실제 공급자 확인, 브라우저 확인, 현장 검증을 따로 보고한다 | W7 |
| 파일 경로를 요청 인자로 받지 않고 서버가 발급한 ID로만 접근한다. 단순 세션 ID를 인증으로 보지 않는다 | W3, 서비스 외부 공개 결정 |

저장소와 맞지 않거나 막힌 점: (1) 이미지 생성 어댑터 위치를 `cont.generation`으로 제안하지만, 앞서 정한 대로 생성 모델 어댑터는 생성형 AI 공통 기반에 둔다. 위치는 열린 결정이다. (2) 실제 공급자 시험에는 자격 증명이 필요하며 이 세션에는 없다. (3) 작업일 수와 일정은 가져오지 않는다.

## 공개 화면 검토와 개편 명세 (2026-11-24 검토)

공개 Studio, Physics, Fab 화면을 직접 조작해 본 검토와 개편 명세다. 원칙은 [roadmap.md](roadmap.md) 4-1의 X로 올렸다.

## 아직 가져오지 않은 것

- 표시 상태(화면의 보기 설정)와 물리 값을 분리하는 규칙. 화면 쪽 코드가 더 생긴 뒤 규칙으로 만든다.
- 선행 단계, 단위, 불확실성이 없으면 계산하지 않는 "닫힘" 규칙. 지금은 영역별 입력 검사로만 있다.
- 병렬 개발에서 폴더 소유권을 나누는 규칙. 지금은 대표 한 명이 병합한다.

## 가져오지 않기로 한 것

- 11개 기술 층의 구조와 12개 에픽: 이 저장소는 7개 모듈(C1~C7)로 시작했다. 필요한 부분만 모듈에 대응시킨다.
- 옛 엔진 이름과 문서 체계: 이름이 아니라 필요한 일만 가져온다.
- 많은 워크플로와 보고서 문서: 옛 저장소가 불어난 원인이므로 점검 세 가지와 상태 파일 하나로 시작했다.

## 아직 정해지지 않은 것

대표 PC의 정본 문서 묶음은 스스로 "최종 아님"이라고 적고 있다. 어느 판을 기준으로 삼을지, 어떤 부분을 공개 저장소 문서로 옮길지는 대표가 정한다. 정하기 전에는 이 표만 늘린다.

## 제품화 필수 AI 모형 개발 계획 (2026-11-25 입력)

필수 AI 기능 열 개(M01~M10), 모형별 데이터·학습·평가 방법, 데이터 누출 방지 규칙, 개발 실행 명령을 담은 개발 제안 두 건을 읽었다. 같은 내용의 요약본과 상세본이다.

저장소와 맞지 않거나 막힌 점: (1) 명세의 Quantity가 `cont.answer.Quantity`와 이름이 같아 그대로 만들 수 없다. (2) 수치 목표와 18주 일정은 제안이라 옮기지 않았다. (3) 명세는 저장소에 해당 기능이 이미 있다고 주장하지 않는다고 적었고, 이 저장소의 실제 현황은 docs/models.md의 대조표가 맡는다.

## 생성형 AI 제품 중심으로 우선순위 확정 (2026-11-25 후속 대표 지시)
