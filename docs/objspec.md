# 공통 대상 명세 (objspec)

> 상태: 보조

같은 대상을 설명 이미지·3D·4D·그래프가 **같은 부품 ID**로 가리키게 하는 명세다. 로드맵 Y9의 첫 구현이며, 3D 장면·단계 4D·이미지 요청은 이 명세를 읽는다(그래프 연결은 아직 없고, 저장·재열기는 `service.project`가 맡는다). 구현 위치는 `src/cont/objspec/`.

## 무엇을 하나

| 질문 | 답 | 코드 |
|---|---|---|
| 이 그림의 "위 다이"는 3D의 어느 부품인가 | 부품 ID `die.si` | `ObjectSpec.part(id)` |
| 구조가 바뀌었나 | 내용 해시 `version`이 달라진다 (부모 version은 해시에 넣지 않는다) | `ObjectSpec.version` |
| 이 표현이 명세와 맞나 | 빠진 부품·모르는 ID·이름 불일치·다른 version을 나눠 보고한다 | `check` |
| 부품을 고치면 무엇을 다시 만들까 | 바뀐 부품을 가리키는 표현만 고른다. 카메라·속도 변경은 아무것도 고르지 않는다 | `affected` |
| 카메라를 돌리거나 한 단계만 느리게 하면 | `ViewState`만 바뀌고 구조 version은 그대로다 | `ViewState` |

## 첫 대상: 본딩 층 구조

`hybrid_bonding_stack()`은 아래 웨이퍼·아래 유전층·위 유전층·위 다이 네 부품과 접근·정렬·접촉 세 단계를 만든다. **치수는 설명용(`illustrative`)이며 실측이 아니다.** 사용자가 `edit_part`로 고치면 `user_input`이 된다. 단계의 시간 축은 공정 단계 순서(`process_stage`)이고 물리 시간이 아니다. 접합 품질·온도·응력은 이 명세에 없다.

## 3D 장면과 단계 4D 재생

`Timeline(spec, view)`가 단계별 길이(기본 2초 ÷ 속도, `config/objspec/playback.yaml`)와 부품별 자세를 정한다. 시작 자세(`start`)에서 단계 끝 자세로 smoothstep으로 움직이고, 단계에 없는 부품은 제자리다. `view/scene4d.py`는 같은 식을 JS로 돌려 WebGL 한 파일 HTML을 만든다(재생·멈춤, 위치 막대, 단계 버튼, 끌기·휠·키보드 카메라, 처음 시점 복귀, 자동 재생 없음). 속도를 바꾸면 그 단계 길이만, 카메라를 바꾸면 시점만 달라지고 부품 모양과 구조 version은 그대로다. 시험이 JS와 Python의 자세 값을 맞춰 보고, 실제 Chrome에서 그려지고 재생되는지 확인한다.

**부품 직접 선택.** 장면을 누르면 그 자리에 보이는 부품이 선택된다(부품마다 다른 색으로 따로 그린 화면을 읽어 알아내므로 겹친 부품은 앞에 보이는 것이 잡힌다). Shift·Ctrl·⌘를 누르고 누르면 더하거나 뺀다. 5px 넘게 끌면 선택이 아니라 회전이다. 빈 곳을 누르면 비운다. 범례의 부품 단추로도 같게 고를 수 있다(`aria-pressed`). 바뀔 때 `s4d:select` 이벤트가 `{ids, spec_version, source}`를 알리고, 밖에서는 `s4dSelect(ids)`로 강조만 넣을 수 있다(이벤트는 되알리지 않는다). 세션은 `SceneSession.select_from_screen(ids, spec_version)`로 받으며, 명세 version이 다르거나(오래된 화면) 명세에 없는 부품이면 거부하고 이전 선택을 지킨다. 다음 대화의 "그 부품"은 이 선택을 가리킨다. 시험은 실제 Chrome 클릭·Shift 클릭·끌기·작은 떨림·범례 단추를 확인한다. **아직 없는 것:** 이 이벤트를 세션에 잇는 웹 화면(지금은 두 쪽이 각각 시험됐을 뿐 이어져 있지 않다).

## 설명 이미지 연결

`generate_image(spec, generator, stage)`가 명세의 부품 목록과 아래→위 층 순서로 영어 프롬프트를 만들고(문구는 `config/objspec/image_prompt.yaml`), 생성 결과와 같은 부품 ID를 가리키는 `Representation`·기록(명세 version, 단계, 치수 상태)을 돌려준다. 부품을 고치면 `check`가 이미지를 `stale`로 표시하고 `affected`가 다시 만들 표현으로 고른다. 카메라·속도 변경은 이미지에 영향이 없다. **부품 목록은 프롬프트에 적은 것(`parts_declared_by: prompt`)이며, 그림이 그 층을 실제로 그렸는지는 확인하지 않는다.** 가짜 생성기 결과는 `real: false`로 남는다. 실제 모델(SDXL 등)로 돌린 그림의 층 일치는 사람이 보거나 이후 시각 검수가 맡는다.

## 선택한 부분만 고치기 (P4)

`select(spec, "위 다이")`가 부품 ID·이름·층 이름·이름 일부 순으로 찾아 부품 ID를 돌려주고, `select_region(spec, (x0,y0,x1,y1))`는 옆면 단면 도식 위 사각형이 덮은 부품을 고른다(상자의 절반 이상을 덮은 부품, 없으면 중심이 든 부품 하나). 모호하거나 없으면 `SelectionError`로 후보를 알리고 고치지 않는다. `edit_selection(spec, selection, z1=2.4)`는 선택한 부품에만 변경을 적용하고 변경 전후(`diff`)와 그대로인 부품(`unchanged`), 다시 만들 표현(`rebuild`)을 돌려준다. 같은 값으로 고친 것은 변경이 아니다. 단계 하나의 부품 자세는 `ObjectSpec.edit_stage_pose`로 고친다. 층이 겹치게 되는 변경은 막지 않고 `overlaps`로 알린다.

- 영역 선택은 **우리가 그린 옆면 도식(쉬는 자세)** 기준이다. 생성한 그림 위의 영역은 그림에 부품 위치 정보가 없어 풀 수 없다.
- 부품 사이 치수 정합(예: 위 다이가 아래보다 커도 되는가)은 판단하지 않는다.

## 저장과 다시 열기 (P6)

`save_project(root, project_id, name, spec, view, selection, playback_t, images)`가 한 폴더에 `manifest.json`, `files/`(명세 JSON·이미지 PNG), `ledger/`(기존 자료 장부 기록)를 쓴다. 명세는 장부의 원본(source), 고친 명세는 이전 명세를 부모로 둔 파생물, 이미지는 만든 때의 명세를 부모로 둔 파생물이다. `open_project(root)`는 파일만 읽어 같은 명세·카메라·단계 속도·선택·재생 위치·이미지로 복원하며 **모델을 부르지 않는다**. 화면은 `scene4d_page(state.spec, state.view, start_t=state.playback_t)`로 저장한 위치에서 다시 시작한다. `restore_version`은 이력의 이전 명세를 꺼낸다(현재 상태는 다시 저장해야 바뀐다).

| 상황 | 동작 |
|---|---|
| 저장 중 종료 | manifest를 임시 파일에 쓴 뒤 바꿔 넣으므로 직전 정상 저장이 남는다 |
| manifest 손상·손으로 고침(본문 해시 불일치) | 직전 정상 manifest로 열고 `recovered_from_previous`·`problems`로 알린다. 둘 다 못 쓰면 거절 |
| 명세 파일이 없거나 바뀜 | 열지 않는다 |
| 이미지 파일이 없거나 바뀜 | 열되 해당 이미지를 `missing`·`changed`로 표시하고 `problems`에 적는다 |
| 다른 프로젝트의 manifest·폴더 | 거절 |
| 지원하지 않는 저장 형식 버전 | 거절(추측해서 열지 않는다) |
| 동시 저장 | 잠금 파일로 거절. 오래된 잠금(`config/objspec/project.yaml`)은 지운다 |

- **대화 기록:** 장면 대화(`scene_chat`)는 사용자 발화, 계획 단계의 도구·상태·오류, 코드가 만든 답, 요청 ID를 manifest 본문에 함께 저장한다(같은 해시로 보호). 모델의 원문 응답과 공급자 설정·키는 저장하지 않는다. 다시 열면 같은 대화가 복원되어 다음 요청의 문맥("그 부품")으로 쓰인다. `save_project` 단계가 있는 요청은 그 요청 자신까지 기록하고(`save_conversation`, 개정 번호는 올리지 않음), 저장하지 않은 요청은 기록에 없다. 길이는 `config/objspec/project.yaml`의 `conversation_max_turns`·`conversation_text_max_chars`로 제한하며 넘으면 오래된 턴을 버리고 긴 글은 "…(잘림)"으로 표시한다. 대화 기록이 없는 이전 저장도 열린다. 기록이 깨지면 비워서 열고 `problems`에 적는다.
- **중단된 요청 재개:** 이미 저장한 프로젝트에서 장면 대화는 계획을 실행하기 **전에** 요청 기록(발화·검증된 계획·요청 시점 상태 지문)을 `<프로젝트>/pending/request.json`에 남기고, 요청이 끝나면(완료 또는 전부 되돌림) 지운다. 실행 중 프로세스가 죽으면 기록이 남는다. 다시 열면 `open_problems`와 `pending()`으로 알리고, 사용자가 정한다.
  - `resume_pending()`: LLM을 다시 부르지 않고 **같은 계획을 처음부터 다시 실행**한다. 장면의 변경은 저장 전까지 메모리에만 있으므로 끝난 단계를 건너뛰지 않는다(건너뛰면 사라진 변경이 빠진다).
  - `discard_pending()`: 버린다.
  - 거절하는 경우(기록은 지우지 않고 이유를 알림): 열었을 때 상태가 요청을 받던 때와 다름(저장하지 않은 변경이 사라졌거나, 계획이 저장 단계까지 실행되어 개정이 달라짐), 기록이 깨졌거나 해시가 맞지 않음, 지금의 도구로 계획 검증이 안 됨.
  - 기록이 남아 있는 동안 새 요청은 받지 않는다(공급자도 부르지 않는다). 기록을 남기지 못하면 그 요청은 실행하지 않는다. 한 번도 저장하지 않은 프로젝트는 다시 열 수 없으므로 기록하지 않는다.
  - 한계: 저장하지 않은 변경은 중단되면 사라진다(자동 저장 없음). 그 뒤에 온 요청은 위 이유로 이어 갈 수 없다. 이어 실행하면 `make_image` 같은 단계의 모델 호출도 다시 일어난다. 화면(버튼)에는 아직 연결하지 않았다. 시험은 가짜 생성기와 파일로 했고, 프로세스 종료는 `BaseException`으로 흉내낸 시험과 실제 하위 프로세스를 `os._exit`로 강제 종료한 시험 둘 다 있다(PC 재부팅·전원 차단 같은 OS 수준 중단은 확인하지 않음).
- 사용자별 분리와 접근 권한은 없다. 폴더가 곧 프로젝트다.

## 대화로 실행하기 (P1·P2 ↔ Y9)

`SceneSession(spec, generator, provider, root=…, project_id=…)`의 `turn(text)`가 현재 상태(부품 ID·이름, 단계 순번·속도, 카메라, 선택, 재생 위치, 마지막 이미지)와 도구 목록, 최근 대화를 공급자에 보내 계획 JSON을 받고, `dialogue.plan`의 검증을 통과하면 도구를 의존 순서로 실행한다. 도구: `select_part`, `select_region`, `edit_part`, `edit_stage_pose`, `set_stage_speed`, `set_camera`, `seek`, `make_image`, `compare`, `save_project`. 답문은 도구 결과로 코드가 만든다.

- 계획이 JSON이 아니거나 등록되지 않은 도구·잘못된 인자·빈 계획이면 **아무것도 실행하지 않고** 이유를 알린다. 공급자가 없거나 오류여도 같다.
- 단계가 하나라도 실패하면 이번 요청의 변경(선택·이미지 포함)을 모두 되돌린다. 모호한 부품 지정은 후보를 알리고 실패한다.
- 요청마다 새 실행기를 써서 같은 계획을 나중에 다시 내도 이전 결과를 재사용하지 않는다.
- `SceneSession.open(root, …)`은 저장된 프로젝트를 모델·공급자 호출 없이 연다.
- 가짜 생성기로 만든 이미지는 답문에 "실제 생성 아님"으로 밝힌다.
- **시험은 정해진 계획을 돌려주는 가짜 공급자로 한다. 실제 LLM이 이 계획을 안정적으로 내는지는 확인하지 않았다**(실제 공급자 반복 측정은 후속). 대화 이력은 프로젝트에 저장하지 않는다.

### 계획 품질 측정

`python -m cont.dialogue.scene_eval --llm <공급자> --out result.json`이 `config/dialogue/scene_eval.yaml`의 사례(속도·카메라·재생 위치·부품 수정·이미지·정정·"그 부품"·모호한 지정·없는 대상·값 없음·저장 후 열기)를 새 세션에서 반복 실행하고 **최종 상태**를 코드가 검사한다(요청에 없는 변경도 실패). 공급자 종류별 성공·거절·실패 횟수와 소요시간 중앙값·최대를 JSON으로 남긴다. 측정기 자체는 "올바른 계획을 내는 가짜 공급자"와 "계획을 안 내는 공급자"로 시험한다. 이 측정은 계획기만 본다(이미지 모델·물리 값은 대상 아님). 제품 목표 수치는 첫 기준 측정 뒤에 정한다.

**첫 실제 측정 (2026-11-26, 로컬 Ollama `gpt-oss:20b`, RTX 5080 16GB, temperature 0, 13 사례 × 3회 = 39회):**

| 단계 | 통과 | 비고 |
|---|---|---|
| 지시문 수정 전 | 36/39 | 실패는 모호한 지정 사례 3/3: 모델이 '유전층'을 아래·위 중 하나로 **추측해 수정**함 |
| 수정 후(모호하면 빈 계획을 답하라고 명시) | 39/39 | 거절 9회는 모두 기대한 것(없는 대상·값 없음·모호한 지정) |

호출당 소요시간은 중앙값 1.3초, 최대 5.8초(처음 호출은 모델을 올리느라 더 걸림). **해석 주의:** 수정은 실패한 그 사례를 보고 정한 것이라 39/39는 같은 사례에서의 재측정이다. 수정이 일반적으로 통한다는 근거가 되려면 보지 않은 사례(다른 모호한 지정, 다른 표현)로 다시 재야 한다. 사례는 13개·한 모델·한 번의 측정이며 제품 목표 수치는 아니다. 클라우드 모델(Claude·GPT 등)은 측정하지 않았다.

| 모델 | 통과 | 실패한 사례 |
|---|---|---|
| `gpt-oss:20b` | 72/78 | `u_it_follow_edit` 0/3, `u_undo_by_restating` 0/3 |

- **모호·없는 대상·물리 값·질문만 하는 사례 10개(30회):** `gpt-oss:20b` 30/30. `mpai-gpt-oss-20b`는 29/30 — "다이 쪽 부품의 z0를 1.5로"에서 1회 `die.si`를 추측해 수정했다(같은 입력인데 3회 중 1회만 그랬다). 모호한 지정에 대한 수정은 보지 않은 사례에서도 대체로 통했지만 이 한 건은 새지 않는다고 말할 수 없다.
- **`u_it_follow_edit`("그걸 바깥 반지름 18로"):** `gpt-oss:20b`는 도구에 없는 항목 이름 `outer_radius`를 만들어 도구가 거부했고(되돌림, 상태 손상 없음), `mpai-gpt-oss-20b`는 JSON 뒤에 글을 덧붙여 계획을 읽지 못했다. 사용자가 "outer"라고 쓰면(`u_edit_outer`) 통과하므로 원인은 한국어 표현 → 항목 이름 대응이 지시문에 없는 것이다.
- **`u_undo_by_restating`("방금 바꾼 건 취소하고 원래 속도로"):** 두 모델 모두 취소하지 않고 같은 속도(0.5배)를 다시 적용했다. 되돌리기 도구가 없고 원래 값이 상태에 없다. 상태는 요청한 것과 다르지만 값이 틀렸을 뿐 위험한 변경은 아니다.
- 나머지 정상 요청 사례(속도 표현 변형·서수·카메라 각 항목·재생 위치·선택·이미지·복합 요청)는 두 모델 모두 3/3.
- 호출당 소요시간 중앙값 1.3~1.4초(`gpt-oss:20b` 최대 27초는 처음 호출).

**해석 주의:** 26개·두 모델·한 번의 측정이고 사례는 내가 쓴 것이라 저자 편향이 있다. 위 실패 두 건은 아직 고치지 않았다. 고치면 이 사례로 조정한 것이 되므로 다시 새 사례로 재야 한다. 제품 목표 수치는 아니다.
